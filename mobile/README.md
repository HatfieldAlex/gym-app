# Training log — five UI directions

Five self-contained React Native prototypes, one per aesthetic direction, plus an
unstyled switcher. Dummy data only, hardcoded in each file. No backend, no navigation
library, no persistence, no UI kit, no animation library, no bundled fonts.

```
mobile/
  App.js              scaffolding switcher — not design work
  DirectionOne.js     terminal
  DirectionTwo.js     notebook
  DirectionThree.js   instrument
  DirectionFour.js    thumb
  DirectionFive.js    diff
  android/            generated by `expo prebuild`, gitignored
```

Each direction file exports a default component that renders standalone and covers all
three screens: mid-session logging, session review, and one exercise over time.

## Two risks on this machine, before anything else

**1. Ubuntu 26.04 is newer than the toolchain.** The pinned versions here are Expo SDK 56
(`expo@56.0.21`, `react-native@0.85.3`, `react@19.2.3`), which is one SDK behind the
current release. SDK 57 / RN 0.86 is the default `create-expo-app` would give you; it is
not pinned here on purpose. SDK 56 is at patch .21 with a template at .35, meaning it has
had a long tail of fixes, and it builds cleanly on Node 22 and glibc as shipped on 26.04.
Both were verified on this machine — the Metro bundle and the Gradle debug build both
completed. Do not "upgrade to latest" as a first debugging move; it changes AGP, Kotlin
and Gradle all at once.

There is **no `babel.config.js`** in this project, and that is deliberate. If you add one
containing `presets: ['babel-preset-expo']`, Metro fails with
`Cannot find module 'babel-preset-expo'`, because npm nests it under
`node_modules/expo/node_modules/` where a root-level Babel config cannot resolve it. Expo's
Metro config applies the preset itself. Leave the file absent.

**2. Snap-installed Android Studio ships its own Java.** `snap install android-studio
--classic` bundles a JetBrains Runtime, and the IDE uses that, not your system
`openjdk-17.0.20`. So the JDK compiling your Gradle build in Android Studio and the JDK
compiling it from your terminal are two different JDKs. When a build succeeds in one place
and fails in the other, check this first:

```bash
java -version                                     # your terminal's JDK
ls /snap/android-studio/current/jbr/bin/java      # the IDE's bundled JDK
```

To make them the same, point Android Studio at the system JDK:
**Settings → Build, Execution, Deployment → Build Tools → Gradle → Gradle JDK** → select
`/usr/lib/jvm/java-17-openjdk-amd64`. Or just build from the terminal and use Android
Studio only for the SDK Manager and Device Manager, which is what the commands below do.

## Environment

Add to `~/.bashrc`:

```bash
# Android SDK
export ANDROID_HOME="/home/a/Android/Sdk"
export ANDROID_SDK_ROOT="$ANDROID_HOME"
export PATH="$PATH:$ANDROID_HOME/platform-tools"
export PATH="$PATH:$ANDROID_HOME/emulator"
export PATH="$PATH:$ANDROID_HOME/cmdline-tools/latest/bin"
```

Then `source ~/.bashrc`. Verify with `adb version` and `echo $ANDROID_HOME`.

`ANDROID_SDK_ROOT` is deprecated in favour of `ANDROID_HOME`, but some tooling in the RN
ecosystem still reads it. Setting both costs nothing.

No `JAVA_HOME` line is needed — system OpenJDK 17.0.20 is already the default and Gradle
finds it.

## SDK Manager

Android Studio → **More Actions → SDK Manager**. Tick **Show Package Details** in both
tabs, or you cannot select specific versions.

Already present on this machine: `platform-tools` 37.0.1, `emulator` 37.1.11,
`build-tools;36.0.0`, and `platforms;android-37.0`. Note that the installed platform is
**API 37**, while this project compiles against **API 36** — that mismatch is the single
most likely cause of a first-build failure here.

**SDK Platforms tab — tick:**

- `Android 16.0` → **Android SDK Platform 36** — this is `compileSdk` and `targetSdk` for
  RN 0.85
- `Android 16.0` → **Google APIs Intel x86_64 Atom System Image** — required for the AVD,
  and the one thing on this list that nothing will install for you

**SDK Tools tab — tick:**

- **Android SDK Build-Tools 36.0.0** (already installed)
- **Android SDK Platform-Tools** (already installed)
- **Android Emulator** (already installed)
- **NDK (Side by side) 27.1.12297006** and **CMake 3.22.1** — `expo-modules-core` and the
  app's own Fabric glue compile C++ under the new architecture, so these are genuinely
  needed, contrary to what is often said about RN 0.8x not needing an NDK
- **Android SDK Command-line Tools (latest)** — not currently installed; without it you
  have no `sdkmanager` or `avdmanager` on the command line

In practice the first Gradle build downloaded **platform 36, NDK 27.1.12297006 and CMake
3.22.1 by itself** on this machine — AGP auto-installs missing SDK packages when
`$ANDROID_HOME/licenses/android-sdk-license` is present, and it is. So the only item you
must click through the SDK Manager for is the **system image**, because AGP has no reason
to want one. Tick the rest anyway if you would rather see the download in a progress bar
than in Gradle output.

## AVD

Android Studio → **Device Manager → Create Device**:

- Hardware: **Pixel 6** (1080 × 2400, 411 × 914 dp — the viewport all five directions are
  laid out for)
- System image: **API 36, Android 16.0, Google APIs, x86_64**
- Name it something you will recognise, e.g. `Pixel6_API36`
- Leave graphics on **Hardware — GLES 2.0**

KVM is already working here (`kvm-ok` passes, `/dev/kvm` carries an ACL for user `a`), so
no group change and no `sudo` is needed. Start the AVD from Device Manager and leave it
running before you build.

## Commands, in order

From an empty directory, with the emulator already booted and Node 22 on the path:

```bash
cd /home/a/Projects/gym-app/mobile

npm install                       # installs the three pinned deps

npx expo prebuild --platform android --no-install
                                  # generates ./android — safe to re-run, it is idempotent

adb devices                       # expect: emulator-5554   device

npx expo run:android              # builds the debug APK, installs it, starts Metro
```

The first `run:android` is slow: Gradle 9.3.1 downloads itself, then AGP 8.12.0, Kotlin
2.1.20, the React Native Android artifacts, and — as noted above — the NDK, CMake and SDK
platform 36. On this machine that cold build took **2 m 46 s** of Gradle time after the
downloads, producing a 127 MB debug APK. Subsequent builds take seconds.

The APK is that large because `android/gradle.properties` builds all four ABIs. If you are
only ever going to run this on the emulator, cut it to one:

```properties
# android/gradle.properties
reactNativeArchitectures=x86_64
```

That roughly quarters both the build time and the APK. Re-running `expo prebuild` will
reset the file, so treat it as a local tweak, not a project setting.

After the first install, you only need Metro:

```bash
npx expo start --dev-client       # then press `a` to open on the emulator
```

To verify the JavaScript compiles without touching Gradle at all:

```bash
npx expo export --platform android --output-dir /tmp/rn-export
```

Verified on this machine: `npm install` with the pinned versions, `expo prebuild`, a full

## Troubleshooting

**Gradle cannot find the SDK.** Symptom: `SDK location not found. Define a valid SDK
location with an ANDROID_HOME environment variable or by setting the sdk.dir path in your
project's local.properties`. Either export `ANDROID_HOME` as above in the shell you build
from, or write it explicitly:

```bash
echo "sdk.dir=/home/a/Android/Sdk" > /home/a/Projects/gym-app/mobile/android/local.properties
```

`local.properties` is per-machine and is not committed. If instead the error names a
missing platform — `Failed to find target with hash string 'android:36'` — you are missing
**SDK Platform 36**; install it from the SDK Manager. Having API 37 installed does not
substitute for it.

**Metro port conflict.** Symptom: `Port 8081 is running this app in another window`, or the
app loads a bundle from a different project. Find and kill the holder:

```bash
lsof -i :8081                     # or: ss -ltnp 'sport = :8081'
kill <pid>
```

Or move Metro and tell the emulator where it went:

```bash
npx expo start --port 8082
adb reverse tcp:8082 tcp:8082
```

**adb does not see the emulator.** Symptom: `adb devices` prints an empty list, or
`offline`, while the emulator window is clearly running. In order:

```bash
adb kill-server && adb start-server && adb devices
```

If it is still empty, you are probably running two different `adb` binaries — the one
Android Studio bundles and the one on your `PATH`. Check with `which adb`; it must be
`/home/a/Android/Sdk/platform-tools/adb`. If the device shows as `offline`, cold-boot the
AVD: Device Manager → the AVD's ⋮ menu → **Cold Boot Now**. If the emulator never appears
at all, confirm it actually started with hardware acceleration — `emulator -list-avds`
then `emulator -avd Pixel6_API36 -verbose` will print the KVM state instead of failing
silently behind the GUI.

**The build works in Android Studio but not in the terminal, or vice versa.** See risk 2
above. It is almost always the two JDKs.

## The five directions

### One — terminal

Monospace throughout, aligned fixed-width columns, no cards and no borders except a
hairline under a header row. Two colours: a near-black ground and a warm grey ink, with
dimmer values of the same ink carrying all the hierarchy. Logging is editing a row: the
pending set is a `>` line in the same table as the completed ones, with its fields as
inline inputs in the same columns. The history screen includes a text bar chart because
that is what this idiom does instead of a graph.

*Optimises for* information per square inch, and for the feeling that the data is a file
you own rather than a service you visit. Every set in the session is visible at once.
*Sacrifices* discoverability and one-handed use — the touch targets are text-sized, and
nothing tells you what the columns mean.
*Suits* someone who lives in a terminal and would otherwise be keeping this in a
tab-separated file.

### Two — notebook

Serif, wide margins, hairline rules, paper ground. All three screens are stacked in a
single scroll because a journal has no tabs. Sets are typeset as lines rather than table
rows; prescriptions are italic marginalia; unrecorded values are stated in words
("RPE not recorded") rather than dashes. The primary action is a single underlined
phrase, "Write it down". The history screen is mostly prose, with the eight sessions as
short entries under hairlines.

*Optimises for* calm and for reflective reading after the fact. It makes the honest
absence of progress readable as a sentence rather than a flat line.
*Sacrifices* density and speed — it is the worst of the five to actually use between sets,
and shows perhaps a fifth as much per screen as the terminal.
*Suits* someone whose training log is a thinking tool, read more often than written.

### Three — instrument

A readout panel. Fixed grid, fixed column widths, unit labels always rendered whether or
not there is a value under them. Deviation from prescription is the point: every measured
quantity sits next to its target with a signed delta and a tolerance band, and
out-of-tolerance values take the single accent colour the panel owns. Entry is by
increment, not keyboard — instruments have detents, not text fields. Unrecorded fields
read `—` above the word `NOT REC`, never a zero. The review screen ends with a data
integrity block counting exactly what was not recorded.

*Optimises for* seeing intent versus reality without doing arithmetic in your head, and
for a layout where a number never moves between sessions.
*Sacrifices* warmth entirely, and it is dense enough to be a bad first-run experience.
Stepper entry is slower than typing when the value is far from the default.
*Suits* someone running an actual programme against actual prescriptions who wants to know
where they drifted.

### Four — thumb

One question on screen at a time, answered with 66–104 dp targets in the bottom half.
Logging is a three-step sequence — reps, then RPE, then why it ended — with the running
value shown at 56 px in the untouchable top half. "Didn't judge" and "Not recorded" are
first-class buttons, the same size as the real answers, so leaving a field empty is a
deliberate act rather than an omission. The review and history screens keep the same
scale, which means they show very little.

*Optimises for* the twenty seconds between sets: standing, one hand, phone at arm's length,
breathing hard.
*Sacrifices* overview completely. You cannot see the session while logging it, and the
history screen shows eight numbers where the instrument shows forty.
*Suits* someone who has abandoned other logging apps because typing into a small field
while out of breath is genuinely unpleasant.

### Five — diff

The version-control metaphor taken literally. Every set is paired with the same set from
the previous session of the same kind and shown as a two-line hunk: baseline above, today
below, delta on the right. A session review is a changeset — blocks are `~` changed, `+`
added, `−` removed, with a header naming head and base. Logging works the same way: the
controls are `−1`, `same`, `+1` against the baseline, so you record the change and the
absolute value follows. No red and green; direction is carried by arrows, weight and a
single slate accent. Sets are matched by position, and a set with no counterpart is shown
as added or removed rather than paired with something it is not.

*Optimises for* the actual question — is this different from last time, and in which
direction — and for making a stall impossible to misread as progress.
*Sacrifices* the absolute view. It is poor at "what did I do today" taken on its own, and
it degrades when the session does not resemble its predecessor, which is exactly when a
diff has least to say.
*Suits* someone self-experimenting, who changes one variable at a time and wants the
change itself to be the record.

## Which one I would build

**Three, instrument**, with the staging control from Five.

The stated purpose is self-experimentation, and the data model already separates
prescription from observation. Three is the only direction that treats that separation as
the primary content rather than as metadata: the signed delta against prescription is on
every row of every screen, it never has to be computed by the reader, and the fixed grid
means the same quantity is in the same place in every session you ever look at — which is
the precondition for noticing anything. It is also the only one that renders "not
recorded" with the same visual weight as a value, so a gap in the data stays legible as a
gap. One is denser but flattens intent and observation into the same undifferentiated
columns; Two is the nicest to read and the worst to use mid-set; Four is the best thing
that could happen to your logging discipline and the worst thing that could happen to your
ability to see a pattern. Five has the sharpest single idea, but a diff answers only the
question it is built for, and it has nothing to say about the improvised third exercise
that has no baseline. Three's real cost is that it is cold and has a first-run cliff, and
its stepper entry is slower than typing — which is where Five's relative controls belong:
keep the readout panel, and make entry "same, +1, −1 against last time".
