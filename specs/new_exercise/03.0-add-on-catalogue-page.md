# 03.0 — Add an exercise, on the catalogue page

**Goal:** the exercise catalogue stops being a list you can only read. A name, a
tap, and the movement is in it — and in the list on screen, without a reload.

Needs chunk 02. This chunk builds the form as a **shared component**, because
chunk 04 puts the same form inside a running session.

## Build

1. **A new component**, `frontend-web/src/components/AddExerciseForm.jsx`. It
   owns the box, the button, the request and the failure — and nothing else:

   | Prop | Meaning |
   |------|---------|
   | `onAdded(exercise)` | The created entry, straight from the response. Required. |
   | `onCancel` | Optional. When given, a **Cancel** control is rendered beside Add; when absent, none is. The catalogue page passes nothing — there is nothing to cancel back to — and chunk 04 passes one. |

   Inside: `name`, `busy` and a failure message in `useState`; a `<form>` with a
   labelled text input and an Add button; `onSubmit` preventing the default and
   POSTing `api.post('exercises/', { name })`.

2. **The division of labour, which the rest of the feature leans on:** the form
   owns **failure**, the caller owns **success**. The form made the request, so
   it is the one that can say it did not go through and keep what was typed for
   the retry. What *counts* as success differs by where the form is standing —
   here it is a new row in a list, in chunk 04 it is a movement being recorded —
   so the form hands the created entry up and says nothing about it itself.

   On success: clear the box, leave focus in it, and call `onAdded(created)`.
   Nothing else. Do not render "Added!" inside the component.

3. **Add is off unless there is something to add.** Disabled while the box is
   blank or only whitespace, and while `busy`; the label reads `Adding…` while
   the request is in flight, as the buttons on the session page do. The box
   itself stays enabled — a slow request must not eat a correction being typed —
   but a second submit is refused while one is running (N8).

4. **Send the name as typed.** No trimming, no case fixing, no collapsing in the
   client. Chunk 02 normalises on the way in and that is the only place it
   happens (N9); a second, subtly different rule in the browser is a bug waiting
   for the day the two disagree. The blank check in step 3 is the one exception,
   and it decides only whether a button is enabled, never what is sent.

5. **Failure gets a line under the button** — "Could not add that exercise.
   Please try again." — with the typed name still in the box. `console.error` the
   error as the other mutations do. **A 400 is a failure like any other in this
   chunk**: chunk 03.5 is what tells a duplicate apart from a real problem, and
   building half of it here means building it twice.

6. **The page holds the list.** `ExerciseCatalogue.jsx` currently renders
   straight from `useLoad`'s `data`. It now needs to change that list, so copy
   the loaded value into state the way `CurrentSession.jsx` does with `session`:
   a `useState(null)` plus a `useEffect` that seeds it when `state === 'ready'`.
   Render from that state; keep `<Status state={state} error={error} />` exactly
   as it is, still speaking for the load and only for the load.

7. **The form goes above the list**, under the `<h1>`, inside a
   `<section className="add-exercise">` with an `<h2>` — "Add an exercise". Above
   rather than below: the list can be long, and the point of the page is no
   longer only to read it.

8. **The new entry joins the list in place.** `onAdded` inserts it in name order
   (`localeCompare`) rather than appending it or re-fetching (N11). Two things
   fall out and both are wanted: the count line above the table updates itself
   because it counts the array, and the row is where the user will look for it
   next time rather than orphaned at the bottom.

   A comment is worth leaving here: the API orders by name in SQLite, which is
   not `localeCompare`, so a name with an accent or an unusual case can land one
   row away from where a reload will put it. That is the accepted cost of not
   re-fetching, and the next load is authoritative.

9. **Say it landed, on the page.** A short line under the form — "Added Front
   squat." — naming the entry, replaced by the next add and cleared when the box
   is typed into again. It is the page's, not the form's (step 2), and it is
   needed precisely because step 8 put the row somewhere in the middle of a long
   list where it is easy to miss.

10. **The empty catalogue changes its tone.** "No exercises yet." was a dead end
    when there was nothing to do about it; with the form on the page it becomes
    an invitation — "No exercises yet. Add the first one above." The form is
    rendered whether the list is empty or not.

11. **Style.** A new `/* Add an exercise */` section in
    [styles.css](../../frontend-web/src/styles.css), after the
    `/* Exercise catalogue */` one — the component is shared, so its styles are
    one block that is not owned by either page. Enough here to lay the box and
    the button out on one line and give the section room; thumb targets and the
    rest of the ergonomics are chunk 05.

## Done when

- `/exercises-catelog` shows an **Add an exercise** section above the table,
  with one labelled box and an Add button.
- Add is disabled until something non-blank is typed, and shows `Adding…` while
  the request runs.
- Typing "Front squat" and tapping Add: the row appears in the table in name
  order, the count above it goes up by one, the box empties, focus is still in
  it, and "Added Front squat." appears under the form.
- A reload shows the same list, from the API, with the new entry in it.
- `"  Front   squat  "` typed into the box stores `Front squat` — the server
  normalised it, and the row shows the normalised name because the row came back
  from the response.
- With the API failing, the message appears under the button, the typed name is
  still in the box, and the table is untouched.
- With an empty catalogue, the page invites the first entry instead of saying
  the list is empty.
- The rest of the page is unchanged: the table, the links to each exercise, and
  `<Status>` all behave as before.

## Do not

- Trim, collapse, lower-case or otherwise rewrite the name before sending it
  (step 4).
- Re-fetch `exercises/` after a successful add (N11).
- Give a duplicate its own handling — that is chunk 03.5, in full, in one place.
- Navigate to the new exercise's page, or anywhere, after adding it.
- Add Edit, Delete, Rename or Retire controls to the table (N2).
- Add fields for muscle group, equipment, category or notes (N3).
- Touch `CurrentSession.jsx` — chunk 04 is where the form goes into a session.
- Rename the `/exercises-catelog` route (N12).
- Change `Status.jsx`, `hooks.js` or `api.js`.

## What the user sees

The exercise catalogue becomes a page you can put something into.

- **An "Add an exercise" section sits above the list**, with one box and one
  button. One box, because a movement here is a name and nothing else.
- **Adding takes a name and a tap.** The button is dead until there is something
  in the box, says `Adding…` while it works, and when it is done the box is
  empty with the cursor still in it — the shape of somebody adding three
  movements in a row, not one.
- **The entry appears in the list, in its place.** Alphabetically, where it will
  be next time, with the count above the table going up by one. Sloppy typing is
  tidied on the way in: `"  front   squat "` arrives as the row `front squat`,
  spacing fixed, capitalisation left exactly as it was typed.
- **A line says what landed.** "Added Front squat." — because in a long list a
  new row in the middle is easy to miss.
- **A failure keeps the sentence.** If the request does not go through, a message
  appears under the button and what was typed is still there to send again.
- **An empty catalogue now asks for something** rather than reporting that it is
  empty.

What the user cannot do yet: add a movement from anywhere but this page, or get a
useful answer when the name is already in the catalogue — for now that reads as
an ordinary failure. Chunk 03.5 fixes the second, chunk 04 the first.
