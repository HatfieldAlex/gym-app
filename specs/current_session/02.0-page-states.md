# 02 — Page states: empty, active, resume

**Goal:** the tab knows whether a session is running, can start one, and comes
back to a running one after a refresh. No logging yet.

Needs chunk 01 on the backend.

- [frontend-web/src/pages/CurrentSession.jsx](../../frontend-web/src/pages/CurrentSession.jsx) — the placeholder you are replacing
- [frontend-web/src/pages/TrainingSessionDetail.jsx](../../frontend-web/src/pages/TrainingSessionDetail.jsx) — the conventions to copy

## Build

Rewrite `CurrentSession.jsx`.

1. **Load.** `useLoad(() => api.get('training-sessions/current/'))`. A 204 comes
   back as `null` from `api.js`, which *is* the "no active session" answer — do
   not treat it as an error. Render `<Status>` for the loading and failed cases,
   as every other page does.

2. **Hold the session in state.** Later chunks add sets to it, so the loaded
   value cannot stay read-only:

   ```jsx
   const { state, data, error } = useLoad(() => api.get('training-sessions/current/'))
   const [session, setSession] = useState(null)
   useEffect(() => {
     if (state === 'ready') setSession(data)
   }, [state, data])
   ```

   Everything the page renders reads from `session`; chunks 02.1–06 only ever call
   `setSession`. Keep this shape — it is the seam the rest of the tab hangs off.

3. **No active session** (`state === 'ready' && !session`): one large **Start
   session** button, and nothing else on the page. No options, no form, no
   preamble — starting a workout is a single tap.

4. **Starting.** POST `training-sessions/` with an empty body, put the response
   into `session`, disable the button while the request is in flight. On
   failure, leave the empty state up and show a short message near the button —
   `<Status>` is for the initial load, so this needs its own line.

5. **Active session** (`session` is set): the heading, plus a line of meta in the
   style of the detail page — the start time, e.g. "Started 18:42". Below that
   the page is **two sections, in this order**, and nothing else:

   ```jsx
   <section className="record-set">
     <h2>Record new exercise</h2>
     {/* chunks 03.0–03.8: exercise picker, weight, reps, Log set */}
   </section>

   <section className="completed-exercises">
     <h2>Completed exercises</h2>
     {/* chunk 02.1: the ordered list of what has been logged */}
   </section>
   ```

   Build both sections and both headings now, each holding a one-line
   placeholder paragraph. Chunks 03 and 04 replace only the placeholder inside
   their own section; neither adds, moves or renames a heading. Chunk 06's End
   button goes after the second section — leave clear space for it, but do not
   stub a button that does nothing.

6. **Resume is free** — a page load with an open session finds it through
   `current/` and lands in the active state. There is nothing to build for it
   beyond step 1, and nothing to store locally (A7). Say so in a short comment
   rather than adding machinery.

7. **Title.** `useDocumentTitle` — "Current session — Gym App" either way.

## Done when

- With no open session: one Start button, nothing else.
- With an open session: exactly two headed sections, "Record new exercise"
  above "Completed exercises", each with its placeholder line.
- Start session → the page switches to the active state without a reload, and
  a new row exists in the API.
- Refresh, navigate to another tab and back, or close and reopen the browser →
  still the active state, same session.
- Ending the session by hand (`POST .../{id}/end/` via curl) then refreshing →
  back to the empty state.
- With the backend stopped, the page shows the standard `<Status>` error rather
  than the empty state — "no session" and "could not load" must not look alike.

## Do not

- Write anything to `localStorage` or `sessionStorage`.
- Add the route or the nav link; both already exist.
- Build the logging form, the list, or the End button — chunks 03.0–03.8, 02.1, 06.
- Add a spinner, toast or modal library.

## What the user sees

The first visible change of the whole build. The Current Session tab stops being
a placeholder.

- **Opening the tab with no workout running** shows one large **Start session**
  button and nothing else. No form, no options, no explanation to read — the tab
  asks one question and takes one tap to answer it.
- **Tapping Start session** switches the page in place, with no reload and no
  navigation, to the active-session view: the heading, a line saying when the
  workout began ("Started 18:42"), and two empty sections — **Record new
  exercise** above **Completed exercises**. Each currently holds a single
  placeholder line; the working parts arrive in chunks 02.1 and 03.0–03.8, in those
  sections, without anything moving.
- **The workout survives leaving.** Refreshing the page, switching to another
  tab and coming back, or closing and reopening the browser all return to the
  same running session rather than to the Start button. There is nothing to
  re-tap and nothing to restore by hand.
- **A failure looks like a failure.** If the app cannot reach the server, the
  tab says so in the standard way the other pages do — it does not quietly show
  the Start button as though there were simply no workout running. Those two
  states are told apart on purpose.
- **A failed start says so.** If tapping Start session does not work, the button
  stays where it is with a short message beside it, and the user can tap again.

What the user cannot do yet: log anything, or end the session from the page. The
tab can be started and resumed, and that is all.
