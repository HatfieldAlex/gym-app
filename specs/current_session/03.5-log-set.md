# 03.5 — Log a set

**Goal:** type weight and reps, tap once, and the set is saved — appearing at
once under the held exercise and in the section below.

Needs chunk 03.2. This is the chunk that writes; the three around it do not.

## Read first

- `CurrentSession.jsx` as chunk 03.2 left it
- [observations/serializers.py](../../backend/observations/serializers.py) — the
  exact fields `performed-exercises/` and `performed-sets/` accept
- [api.js](../../frontend-web/src/api.js) — `api.post`, and what a non-2xx does

## Build

1. **The inputs**, under the held exercise's sets: **Weight (kg)** and **Reps**,
   both `type="number"`, `inputMode="decimal"` and `inputMode="numeric"`
   respectively so phones offer the right keypad, and a **Log set** button.

2. **Validation before any request.** Reps must be present and a positive whole
   number. Weight may be left blank — bodyweight movements have none (A5) — and
   a blank weight is sent as `null`, not `0`. Keep **Log set** disabled while
   the entry is invalid rather than failing after the tap.

3. **Logging is up to two requests.**

   - If this session has no `PerformedExercise` for the held definition yet,
     `POST performed-exercises/` with `{ training_session, exercise_definition }`
     and add the result to `session.performed_exercises` with an empty
     `performed_sets: []`, since that serializer does not return the key.
   - Then `POST performed-sets/` with `{ performed_exercise, weight_kg, reps }`,
     and append the response to that exercise's `performed_sets`.

   Holding an exercise already trained in this session reuses the
   `PerformedExercise` already there (A6) — never a second one.

4. **Sticky values.** After a successful log, weight and reps stay filled in
   with what was just logged, so a second set of the same thing is one tap. The
   hold does not change either. Only 03.0's **Change exercise** clears anything.

5. **In flight.** Disable **Log set** until the request settles (A9) so a double
   tap cannot log twice. On failure, keep every typed value exactly as it is and
   show a short message beside the button; nothing else on the page changes.
   Both of these are part of writing the request, not a later pass.

6. **Where the state goes.** Every update is `setSession` on the existing
   object — no second copy of the log, and no refetch of `current/` after a
   write. Both lists redraw because both read that state: confirm that, do not
   wire a second path.

## Done when

- **Log set** stays disabled with reps empty, with reps `0`, with reps `-3`,
  and while a request is in flight.
- Logging a set with weight blank succeeds and stores `weight_kg: null`.
- Logging three sets of the held exercise creates **one** `PerformedExercise`
  and three `PerformedSet` rows, in order.
- After logging, weight and reps are still filled in; tapping **Log set** again
  immediately logs an identical second set.
- Holding a different exercise, logging, then holding the first again reuses the
  first `PerformedExercise`.
- Each logged set appears at once both under the held exercise and in
  **Completed exercises**, with no refresh and no second request.
- A refresh at any point shows everything logged so far.
- With the backend stopped, **Log set** fails visibly, every typed value
  survives, and one tap after the backend returns logs exactly one set.
- A double tap logs one set, not two.

## Do not

- Refetch `training-sessions/current/` after logging.
- Create a `PerformedExercise` before there is a set to put in it.
- Add optimistic UI or rollback machinery (A9).
- Add fields for `distance_m`, `duration_s` or `rpe`, a unit toggle, a notes box,
  or a rest timer.
- Add editing or deleting — chunk 05.
- Add a second button for finishing the exercise — 03.8.

## What the user sees

The tab starts actually recording a workout.

- **The held exercise gains a weight box, a reps box and a Log set button**,
  under the sets it already has.
- **On a phone the right keypad comes up** — a decimal pad for weight, a number
  pad for reps.
- **Log set stays greyed out until the entry makes sense.** Reps blank, `0` or
  negative, and the button cannot be tapped. The user finds out before tapping
  rather than after.
- **Weight may be left blank** for bodyweight movements. That is a valid set,
  not a mistake, and it records as having no weight rather than as `0 kg`.
- **One tap logs one set**, saved immediately and visible in both lists at once.
  Nothing is lost if the phone is locked or the page is closed.
- **A second set of the same thing is one more tap.** Weight and reps stay
  filled in with what was just logged, so repeating a set means tapping again.
- **Going back to an earlier exercise continues it** rather than starting a
  second entry for the same movement — three sets of bench press are three sets
  of one bench press block, whatever order the workout wandered in.
- **A double tap cannot log twice**: the button is inert until the set has
  saved.
- **If saving fails**, a short message appears beside the button and nothing
  typed is lost — the same values are still there to try again.

What the user cannot do yet: say they are *done* with an exercise. Until 03.8
the only way back to the dropdown is **Change exercise**.
